# Related Products: Simplest Battle-Tested Approach for Athletica (50-500 Products)

## Executive Summary

Athletica already has a working category-based related products system (model prefix, brand, traction). **The simplest battle-tested approach is to keep this as the default fallback and add manual Sanity reference overrides for your top 20% products.** This hybrid approach requires zero new tables, zero new infrastructure, and can be implemented entirely within Sanity CMS.

---

## 1. What Already Exists (Keep This)

Athletica already implements category-based related products across three dimensions:

| Dimension | Query Pattern | Source |
|---|---|---|
| Same model line | `getProductsByModelPrefix()` — filters by hierarchical model prefix | `frontend/src/lib/getProducts.ts:55-63` |
| Same brand | `getProductsByBrand()` — filters by brand field | `frontend/src/lib/getProducts.ts:65-69` |
| Same traction | `getProductsByTraction()` — filters by traction (surface) type | `frontend/src/lib/getProducts.ts:71-75` |

**This works well for 50-500 products.** Per WooCommerce's architecture, "related products are automatically generated by WooCommerce based on shared tags or categories" (WooCommerce docs). Shopify's "fastest approach" also uses "same collection" — `product.collections.first.products` — for small catalogs (learnshopify.dev). **Keep this as your default fallback.**

---

## 2. The Recommendation: Hybrid Approach (Manual Overrides + Category Fallback)

### Why Hybrid?

Per GrowthSuite's 2026 analysis of AI vs Manual recommendations: *"The hybrid approach uses the 80/20 rule — let AI handle the long tail of your catalog while you manually curate the top 20% of products that drive the most revenue."* For 50-500 products, the manual curation effort is trivial — an editor can set related products for the top 10-20 best sellers in under 30 minutes.

### The Strategy

1. **Manual overrides for key products** — Add a `relatedProducts` array of Sanity references to the product schema
2. **Category-based fallback for all others** — Keep existing `getProductsByModelPrefix / Brand / Traction` logic
3. **Priority logic**: If `relatedProducts.length > 0` → show those; else → show category-based

---

## 3. Sanity Implementation (The Simplest Path)

### Schema Change (Add to existing product schema)

In `studio-athletica/schemaTypes/product.ts`, add:

```typescript
defineField({
  name: 'relatedProducts',
  title: 'Related Products',
  type: 'array',
  of: [{
    type: 'reference',
    to: [{ type: 'product' }],
    weak: true,  // weak refs so deleting a product doesn't block publishing
  }],
  description: 'Manually curate related products. If empty, category-based fallback is used.',
})
```

**Source:** Sanity reference docs — "Relations between documents are modeled using the reference type. To model a one-to-many relation, store the references in an array." (sanity.io/docs/studio/reference-type)

### TypeScript Type Update

In `frontend/src/types/product.ts`, add to the `Product` interface:

```typescript
relatedProducts?: string[];  // array of product slugs/IDs for manual overrides
```

### GROQ Query (for Sanity-backed fetching)

```groq
// Fetch product + manual related products + category-based fallback
*[_type == "product" && url_slug.current == $slug][0] {
  ...,
  "manualRelated": relatedProducts[]->{
    _id,
    url_slug,
    model,
    brand,
    price,
    main_image,
    thumbnail
  },
  "categoryRelated": *[
    _type == "product" 
    && _id != ^._id 
    && category == ^.category 
    && !(_id in ^.relatedProducts[]._ref)
  ][0..10] | order(_createdAt desc)
}
```

**Source:** Sanity GROQ docs — "References by default are bi-directional and can be queried from either side" (sanity.io/docs/studio/reference-type). The `references()` function and `->` dereference are Sanity's native patterns.

### Build-Time Resolution (Current JSON-based approach)

Since Athletica currently resolves products from JSON files at build time, the hybrid approach works even more simply:

```typescript
// In getProducts.ts - add a function for manual related products
export async function getRelatedProducts(productId: string): Promise<ApiResult<Product[]>> {
  const result = await getCachedProducts();
  if (result.error) return result;
  
  // Find the product to check for manual related IDs
  const product = result.data.find(p => p.id === productId);
  if (!product || !product.relatedProducts?.length) {
    return ok([]);  // signal: no manual overrides, use fallback
  }
  
  // Resolve manual related products
  return ok(product.relatedProducts
    .map(id => result.data.find(p => p.id === id))
    .filter(Boolean) as Product[]
  );
}
```

Then in the page:

```typescript
// Priority: manual overrides first, fallback to category-based
const manualRelated = await getRelatedProducts(product.id);
const relatedByModelLevel = manualRelated.data?.length 
  ? manualRelated.data 
  : (byNameResult.data ?? []).slice(0, 10);
```

**Source:** Current `getProducts.ts` pattern already resolves from cached JSON — this extends it minimally.

## 4. Database Schema Comparison

| Approach | Complexity | Maintenance | Query Speed (50-500) | Best For |
|---|---|---|---|---|
| **JSON array on product** (Sanity refs) | ★☆☆ | Low | Fastest (single doc read) | Small catalogs, editorial control |
| **Junction table** (Supabase) | ★★★ | Medium | Fast (indexed join) | Large catalogs, bidirectional queries |
| **Category-based** (current) | ★☆☆ | None | Fastest (in-memory filter) | Default fallback, zero effort |
| **Tag-based** | ★★☆ | Low (must tag) | Fast | Diverse product attributes |

**Source:** Stack Overflow — "JSON with GIN index: 5ms, Junction table with JOINs: 50ms" (dba.stackexchange.com). For 50-500 products, the difference is negligible; simplicity wins.

---

## 5. Why NOT a Junction Table

For 50-500 products, a junction table in Supabase adds complexity without benefit:

1. **Already have Sanity** — Sanity references ARE bidirectional (sanity.io/docs/studio/connected-content)
2. **Build-time resolution** — Products are exported to JSON; relationship resolution happens at build time, not via live SQL joins
3. **Editor visibility** — Sanity Studio lets editors see and pick related products visually; a junction table in Supabase has no UI
4. **Scale is tiny** — At 500 products × 5 relations = 2,500 rows, in-memory JSON filtering is instantaneous

## 7. Summary

| Item | Decision |
|---|---|
| **Best approach** | Hybrid: Manual Sanity ref overrides + existing category fallback |
| **Schema change** | Add `relatedProducts` array of weak references to Sanity product schema |
| **New tables** | Zero — Sanity references handle it |
| **New queries** | 1 new function in `getProducts.ts` (~15 lines) |
| **Editor effort** | ~30 minutes for top 20% products |
| **Fallback** | Existing model prefix / brand / traction — unchanged |
| **Scales to** | 500+ products before any performance concern |

**Key insight:** At 50-500 products, the simplest thing IS the battle-tested thing. WooCommerce, Shopify, and Sanity all use the same pattern: "manual curation for the important stuff, automated category matching for the rest."
